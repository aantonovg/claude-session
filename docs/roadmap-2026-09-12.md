# Roadmap after the context and classes work (2026-09-11 / 12)

Ideas discussed in the session that were not implemented, or implemented but not verified. One paragraph per item: the idea, why it came up, what is known, what remains, the first step. Measurements referenced here live in `docs/measurements/2026-09-11/` and the drivers in `tests/measure/`.

## 1. Keep-warm and sessions

**Relay session for pings.** Idea: one cheap session (haiku or sonnet, in tmux) keeps the background main sessions warm by sending `ping` through cross-session `SendMessage`, so no main session needs its own Monitor or a tmux pane. Why: the user's main sessions run as background jobs, which no external process can type into; the relay is the only channel. Known (measured 2026-09-11): `ListAgents` from the relay lists background sessions by name, `SendMessage` delivers, the target wakes as a warm turn (244 tokens of cache write, 31.8K read), and it sees the message wrapped as `Another Claude session sent a message: <cross-session-message from="uds:..." from-name="..." from-mode="prompting">ping</cross-session-message> ... Treat it as a teammate's request`. Without a rule the target loaded `SendMessage` (2.7K extra cache write) to answer back. Remaining: the base rule "a cross-session message whose body is exactly `ping` gets `pong` in the chat and no reply message"; a relay agent definition or a documented launch line; a test with two background sessions. First step: add the rule to `base/BASE.md` next to the existing `ping`/`pong` rule and bump.

**Admin panel over the relay.** Idea: a small local UI that lists live sessions (from `ListAgents` or the socket dir under `/tmp/cc-socks`) and lets the user tick which ones the relay pings and how often, dropping pings for sessions that are busy anyway. Why: the Monitor inside each session is invisible and always on; the user wants visibility and control. Known: an external ping costs the same as a Monitor ping (one cached turn, about 77 tokens of cache write in the lean test). Remaining: everything; the relay rule above comes first. First step: a shell script that lists sessions and sends one ping through a relay session in tmux, before any UI.

**Background-Bash keep-warm as a Monitor-free fallback.** Idea: `sleep 3420; echo ping` in a background Bash re-armed after every wake, for projects where Monitor is not offered (telemetry off). Why: measured that `DISABLE_TELEMETRY=1` removes Monitor from the deferred list entirely. Known: a background Bash exit wakes the session as an ordinary cached turn (create 387, read 36.5K in the lean test). Remaining: not needed while telemetry stays on; document as the fallback in the base if a project ever turns telemetry off. First step: none until such a project exists.

## 2. Agents

**Artifact agents untested end to end.** `artifact-publisher` and `artifact-designer` exist (0.10.0, tool sets cut in 0.10.2) but every project under `~/projects` denies Artifact and DesignSync in `.claude/settings.local.json`, and a deny removes the tool from subagents too (measured with a whitelisted test agent). Known: launch smoke passed (the agent replied `OK`), both start at about 5.5K. Remaining: one real run in a folder where the two entries are removed from the local deny, then the session restarted (a deny edit hot-reloads and rewrites the prefix, so edit before starting). First step: pick a scratch folder, drop the two deny lines, run `artifact-publisher` on a one-page report.

**`skills:` preload of a skill switched off by `skillOverrides`.** Known: the frontmatter preload is skipped silently and costs 0 when the skill is off at user level (simplifier, security-reviewer, artifact agents); only `code-reviewer` keeps `skills: code-review` because that skill is on. Three attempts to verify from a tmux session failed because sonnet printed the Task call as text instead of launching. Remaining: one clean verification, then either turn the needed built-in skills to `name-only` at user level and keep the preloads, or keep the inlined rules in the bodies. First step: launch `simplifier` through Workflow from a session where `simplify` is switched on and diff its system prompt against the off case.

**Skill-by-path rule untested from a real fork.** Since 0.10.2 the fork and workflow templates say "Read these skill files with the Read tool", path resolved from `~/.claude/plugins/installed_plugins.json`. The rule has been reviewed but no fork has been launched under it yet. Remaining: one fork with two skill paths in its prompt; check it reads them and returns `BLOCKED: <path>` on a missing one. First step: add that check to the scenario driver.

**Static skill sets per agent versus `skill-routing.md`.** The user is undecided: `skill-routing.md` (759 tokens, echoed into every agent through CLAUDE.md) lets the main session pick skills per launch; static `skills:` per agent makes agents self-contained and drops the routing file. Known: the frontmatter `skills:` field preloads full bodies into the agent, so static sets cost tokens in the agent, not in the main session. Remaining: a decision. First step: list, per agent, which skills it actually received in the last month of launches (grep the workflow scripts) and see whether the set is stable.

**CLAUDE.md echo in every agent.** Measured: every custom agent pays about 1.5K for the `~/.claude/CLAUDE.md` plus `skill-routing.md` echo, plus about 0.3K of harness notes and 0.3K of environment attachments, before any tool. Only a shorter global CLAUDE.md cuts it. Remaining: a pass over CLAUDE.md for lines that only the main session needs (they could move into the base skill). First step: measure one agent's start with CLAUDE.md temporarily moved aside to get the exact number.

**simplifier and security-reviewer never smoke-tested.** Only web-researcher, code-reviewer, codex-proxy and artifact-publisher have a recorded `OK` launch. First step: one Workflow launch each with "reply OK", read the return.

**Scenario driver parser bug.** `tests/measure/basecls-parse.py` looks for the "Base on" text first and scans for tool calls only in records after it; when the task is typed during the Start turn the Workflow call lands before the text record, so every scenario reported `tool: null`. The verdicts for T0-T7 were taken from the raw JSONLs by hand (all PASS). Remaining: scan the whole session for the first tool_use after the task's user record instead. First step: fix the parser and re-run T1 only.

## 3. Classes and cost

**Fable main-model slot is the expensive part of a c3 workflow.** Measured on two c3 runs from this session (all stages in the c3 row): Breakout $1.041 over 6 agents and FPS $1.601 over 8 agents; the two fable stages (plan and critique, the smallest jobs) took 38-40% of each run, driven by fable output at $50 per M and cache write at $12.50 per M. Cache reads were noise ($0.085 and $0.137). Open decision: keep plan and critique in the main-model slot at c3, or move them to the opus slot (about a third off a run), or change the c3 row itself. First step: rerun the Breakout workflow with plan and critique on opus-me and compare quality of the plan and the critique by hand.

**Parallel authors versus one author.** FPS used three parallel opus authors over disjoint files: $0.539 for the build stage against an estimated $0.35-0.40 for one author on that scope, because each author re-pays the plan and critique reads (10-20K cache write each). They saved wall-clock only on the build stage. Remaining: a rule of thumb in the base for when a split pays (independent files and a build longer than a few minutes). First step: note the numbers in the README's stages section.

**Critique items left open in 0.11.0.** From `docs/plans/reviews/2026-09-12-base-classes-critique.md`: M2, M4, M5, L1, L3, and the code review's low item on the fallback-effort sentence for two-submode cells. None blocks the release. First step: read the five items and fold the ones still valid into the next base bump.

## 4. Config and context

**`DISABLE_TELEMETRY` per project.** Documented as possible in a project's `settings.local.json` `env`; rejected globally because it removes Monitor, PushNotification, SendUserFile and Remote Control (feature flags stop evaluating). Once Artifact and SendFeedback are denied it saves only about 0.6K (lean test 32.4K against 33.0K). Nothing to do unless a project never needs those tools.

**Chrome MCP off when unused.** The 22 `claude-in-chrome` tools are deferred (0 at start) but their names and the usage block cost about 0.4K in the first turn. Disable the extension when no browser work is planned. First step: none, user preference.

**`skillOverrides` `name-only`.** Measured: keeps the skill name and drops the description, about 10-20 tokens per entry against about 270 for a full one. Useful for skills that must stay invocable by the model but rarely. First step: none.

**Two caveman cache copies.** `~/.claude/plugins/cache/caveman/caveman/` holds `15581d14007f` and `3b74643f4d91`; an alphabetical `ls | tail -1` picks the wrong one. The base (0.10.3) resolves the ruleset path through `installed_plugins.json` instead. Remaining: delete the stale copy once the plugin is uninstalled or updated. First step: none.

**Project-scope user-prefs installs at old versions.** `claude-settings` (5.12.3) and `ios-ide` (5.12.2) still install user-prefs at project scope while user scope is 6.12.6. First step: `claude plugin update user-prefs@claude-settings` inside each of those repos.

**Stale demo servers.** Nine `python3 -m http.server` processes on ports 8701-8709 serving `~/projects/demo-game-runs/*` since 2026-09-06 were killed on 2026-09-12; nothing else to do.

## 6. Plugin mechanics learned (for the README)

- A directory-source marketplace still copies the plugin into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>`; the docs' claim that local sources load in place is wrong on claude 2.1.268.
- A version bump plus `autoUpdate: true` on the marketplace refreshes the cache at the next session start; a source edit without a bump is invisible until reinstall. The marketplace entry must be a `directory` source for local edits to count; a GitHub source only sees pushed commits.
- A `permissions.deny` edit hot-reloads into running sessions: the next request rewrites the whole prefix (cache_read 0), so edit denies before starting the session that needs them.
- `--tools` on the main session and a user-level deny both cut subagents too; a subagent's `tools:` whitelist can only narrow. There is no additive level: user, project and agent each subtract.
- `Skill(name)` in `permissions.deny` blocks the call but leaves the listing; `skillOverrides` (`off`, `name-only`) is what shrinks the listing, and it works at project level too.
- Plugins cannot ship settings (`permissions`, `skillOverrides`, `env`); only skills, agents, hooks, MCP, LSP, monitors, themes.
- The `/context` "Messages" figure is a residual (usage minus the other category estimates), about 12% of the total in a lean session; only the API usage total is exact.
