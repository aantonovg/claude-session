### 1b. Prompt sizes (new paragraph in "Fork prompt template", after the template block)

> Prompt size. A fork prompt is under 100 tokens: the fork has the whole conversation, so the prompt names the job, the files it owns and the return format, nothing else. A workflow agent prompt is 300-1000 tokens, scaled to the job: inputs by absolute path, never pasted; acceptance criteria; commands; return format. Longer than 1000 tokens means the job should be split or the inputs should be a file the agent reads.

### 1c. Fork vs workflow, model by input volume (replaces the first bullet of "When to fork", lines 115-117, and the "fork" row of the table at line 228)

> Prefer a workflow: a cold agent starts small and its turns are cheap. A fork only when the job is general-purpose (many skills and tools at once) and explaining it cold would cost more than the fork's re-reads of the conversation, or when the job depends on an understanding that lives only in this conversation. Say which in one line before the launch.
>
> Model by input volume. Small input (a few files, a few MCP calls): the main-model slot, as a fork or a cold agent on the main model. Medium input: the opus slot. Large input (sweeps, logs, test output, many files): the sonnet slot. Haiku only inside proxy agents (`claude-code-guide`, `codex-proxy`), never for work.

### 1d. Three slots, five classes (replaces "### One class and one pairing per workflow", lines 300-311, the table rows 228-231 of "Downscale and upscale of intelligence", and the whole "## Mode: sonnet" section, lines 248-260)

> Every launch takes its model and effort from one of three slots: **main** (small input, judgment), **opus** (medium input), **sonnet** (bulk input). The class of the session fixes the three slots:
>
> | class | main slot | opus slot | sonnet slot |
> |---|---|---|---|
> | c1 lowest | opus-low | opus-low | sonnet-low |
> | c2 below default | fable-low | opus-low | sonnet-medium |
> | c3 default | fable-low | opus-medium | sonnet-high |
> | c4 above default | fable-medium | opus-high | sonnet-high |
> | c5 highest | fable-high | opus-high | opus-high |
>
> Roles map onto slots: reviewer-debugger and upscale critique or generation → main slot; plan author/fixer and code/test fixer → opus slot; code/test author → opus slot for small and medium input, sonnet slot for bulk; fact researcher, test/script executor, mechanical sweeps, code review of a diff over 100 lines → sonnet slot; waiter → sonnet slot; codex-proxy and claude-code-guide → haiku, unchanged. Upscale budgets stay: 5 tool calls at medium, 3 at high.
>
> The class is per session, set at `/session:base`; the main session's own model and effort are independent of it (a fable-high main may run c1 workflows). A fork always runs on the main session's model and effort, not on a slot.

Removed by this: the pairing concept (`fable-opus`, `fable-fable`, `sonnet`), the per-pairing map in the README and `~/.claude/session-map.md`, the "Mode: sonnet" section, the phrase "opus-low when the main session is fable", the words "class and pairing in `meta.name`" (lines 304, 334, 459, 466: now "class and submodes").

### 1e. Submodes (new subsection right after the class table)

> Submodes rewrite a slot value after the class row is chosen, in this order: `no-sonnet`, then `no-opus`, then `no-fable`; each maps the current value, so a combination is applied left to right.
>
> | submode | rewrites |
> |---|---|
> | no-sonnet | sonnet-high → opus-medium; sonnet-medium → opus-low; sonnet-low → opus-low |
> | no-opus | opus-high → fable-medium; opus-medium → sonnet-high; opus-low → sonnet-medium |
> | no-fable | fable-high → opus-high; fable-medium → opus-high; fable-low → opus-medium |
>
> Example: `c3 no-sonnet no-fable`: sonnet slot sonnet-high → opus-medium; main slot fable-low → opus-medium; opus slot stays opus-medium. Codex modes (`session:codex`) are unchanged and sit on top.

### 1f. Defaults in agent frontmatter (new paragraph in "### Every `agent()` call", replacing the first bullet at lines 318-319)

> Every plugin agent carries its c3 model and effort in the frontmatter. The `agent()` opts pass `model` and `effort` only when the effective slot value differs from c3 (another class or a submode); with c3 and no submodes the opts carry neither and the frontmatter rules. `agentType` launches (`claude-code-guide`) always pass both. The label prefix `<mod>-<eff>-` names the effective values, frontmatter or override.

Frontmatter table (section 2 below) sets those defaults.

### 1g. Invocation and reply line (replaces lines 27-34 of "Start")

> Arguments, any order: `/session:base [no-sonnet] [no-opus] [no-fable] [c1|c2|c3|c4|c5]`; `/base` is the same command (0.8.10). Default `c3`, no submodes. The reply line, printed once after the monitor exists: `Base on (c3), ping monitor <task id>; forks for every 2+ call job`, with the submodes appended inside the parentheses in the order given above: `Base on (c4, no-sonnet), ping monitor <task id>; forks for every 2+ call job`. There is no variant without a task id. Every workflow `meta.name` starts with the class and the submodes: `c3-<slug>`, `c4-no-sonnet-<slug>`, `c5-no-sonnet-no-fable-<slug>`.

Also: the waiter template at line 402 (`c1-<pairing>-wait-<job>`) → `c1-wait-<job>`; the Forbidden bullet at 466 ("no `meta.name` without class and pairing") → "without the class and the submodes".

## 5. Decisions applied after the critique (2026-09-12, implemented in 0.11.0)

- H1: hard rule 1 = any job of 2 or more tool calls goes to a fork or a workflow; rule 2 = at most 1 own call per turn, except the Start turn (ToolSearch, Monitor, style-file path resolve and Read), the commit, and fork or workflow launches. Rule 5 became the input-volume rule.
- H2: submodes are one explicit 35-cell table in BASE.md and README (class rows, columns none / no-sonnet / no-opus / no-fable / no-sonnet no-opus / no-sonnet no-fable / no-opus no-fable), computed from the single maps; two submodes leave one model; all three = argument error (`invalid arguments` in the reply line, previous setting kept). Verified: no cell lands on a banned model.
- H3: input volume thresholds: small = up to 3 files or under 3K tokens (main-model slot, fork allowed); medium = 4-10 files or 3-15K (opus slot); large = more than 10 files, over 15K, or unknown size (sonnet slot). Unknown counts as large. Haiku only for proxies.
- H4: every `agent()` passes the effective model and effort explicitly; agent frontmatter holds the c3 default as a fallback for direct launches only. Lines 236, 315, 333, 465 kept consistent.
- H5 (corrected 2026-09-12 by the user): "Upscale agents" rewritten in slot terms: main-model slot of the workflow's own class, budgets 5 at medium or lower, 3 at high or above; the class is one setting per workflow, upscaling or downscaling is the whole workflow at another class, never a per-stage step. - Frontmatter defaults (differ from section 2 where noted): stage-reviewer and stage-critic fable/medium; waiter sonnet/low; simplifier opus/medium; artifact agents opus/medium; the rest as in section 2.
- Hook: `base_mode` in `session-modes.sh` accepts any subset of the submodes (not all three) plus at most one class, renders `base[-cN][-no-sonnet][-no-opus][-no-fable]`; 9 new test cases, 81/81 pass.
