## 1. Идея вкратце

У работы субагента четыре независимых аспекта: какие инструменты у него есть, какую роль
он играет, как несколько ролей сотрудничают над одной задачей, и как прорабатывается один
кусок задачи. Сегодня эти аспекты смешаны: файл агента несёт и список инструментов, и
роль, главная модель пишет промпты роли на лету, а порядок ролей на большой задаче каждый
раз выбирает главная модель.

Идея разделяет аспекты и даёт каждому свой носитель:

| аспект | носитель |
|---|---|
| набор инструментов | именованный lean-агент (файл агента) |
| роль | workflow (статический промпт внутри скрипта) |
| фиксированный процесс на куске задачи | более длинный workflow над пулом агентов |
| процесс нескольких ролей на всей задаче | skill, описывающий стадии, task-файлы и user gates; он не называет ни workflow, ни agent, ни tool (3.3) |

Одна настройка пронизывает все четыре: class `c1-c5`, задаваемый один раз в начале
сессии. Только он решает модель и effort каждого агента в каждом workflow.

Главная модель перестаёт изобретать промпты, процесс, модели и мнения review. Она
выбирает процесс, выбирает depth, запускает именованные workflows с аргументами и
записывает результаты в группу task-файлов.

## 2. Четыре аспекта

### 2.1 Набор инструментов (lean-агенты)

Субагент должен видеть только те инструменты, которые нужны для его задачи. Меньше
инструментов — меньший system prompt, меньшая стоимость на холодный агент и меньше
простора для агента выйти за рамки своей задачи (критик без Edit не может «исправить
попутно, пока читает»).

### 2.2 Роль (статический промпт)

Роль — это статический промпт: кто агент, что он возвращает, чего он никогда не делает.
Ключевое свойство из заметки: текст роли **не пишется главной моделью при запуске**.
Промпт, написанный на лету, отличается от запуска к запуску, стоит output-токенов главной
модели и дрейфует вместе с разговором. Статическая роль проверяется один раз, а затем
переиспользуется.

### 2.3 Процесс нескольких ролей над одной задачей

Два подпункта из заметки:

- Задачи сильно различаются по типу (bugfix, feature, research, migration, ops, document,
  review чужого MR). Каждому типу нужна своя последовательность ролей, поэтому процессов
  несколько, а не один. Плагин уже показывает это: `session:pipeline` (своя задача) и
  `session:review` (чужая работа) делят общее ядро и различаются стадиями.
- Работа над задачей — не один непрерывный прогон. Она останавливается ради смены
  направления или human review, а затем продолжается. Поэтому этот уровень не может быть
  одним длинным скриптом workflow: скрипт бежит до конца и не оставляет места
  пользователю. Это должно быть описание, которому главная сессия следует стадия за
  стадией, с состоянием на диске между стадиями.

### 2.4 Фиксированный процесс на куске задачи

Внутри одной стадии порядок шагов известен заранее (author, tests, fixer, до N циклов;
или critic, evidence, triage, fixer). Эта часть не требует ни человека, ни суждения
главной модели, поэтому это детерминированный скрипт.

## 3. Предлагаемые механизмы

### 3.1 Набор инструментов через именованные агенты

- Семейство именованных агентов, различающихся только комбинацией инструментов: от самых
  простых (только Read; Read и Write) до более богатых (Bash, Read, Edit, Write; web;
  MCP).
- Файл агента хранит список инструментов и минимальный общий контракт (форма возврата,
  правило BLOCKED, правило рабочего каталога). Он не содержит роли и модели.
- Инструменты сверх встроенного набора (MCP-серверы, project или корпоративные CLI)
  получают свои файлы агентов в плагине, который несёт этот инструмент, вместе с
  workflows, hooks и skills, сделанными для него (3.7), а не в общем плагине. Общий
  плагин покрывает только встроенные инструменты и остаётся свободным от имён проектов.

### 3.2 Роль на уровне workflow

Роль живёт в скрипте workflow, а не в файле агента. Два вида workflows:

- **One role workflow, одиночные агенты.** Не один workflow на роль: единый workflow
  принимает аргумент `role` и несёт весь каталог одиночных ролей (`critic`, `researcher`,
  `executor`, `translator`, `triage`), каждая как статический промпт роли с типизированными
  аргументами (пути, вопрос, выходной файл). Его usage contract перечисляет роли, которые
  он предоставляет, так что один скрипт и одна строка SessionStart покрывают их все, а
  сопровождение остаётся в одном месте. Workflow превращает нейтрального агента с набором
  инструментов в role-агента; главная сессия запускает его по имени и передаёт только
  аргументы.
- **Более длинный workflow, пул агентов.** Несколько вызовов ролей в фиксированном
  потоке, решающем одну подзадачу: author → tests → fixer с лимитом циклов; параллельные
  researchers → critique → synthesis; critic → evidence-researchers → triage → fixer. Это
  аспект 2.4. Тот же подход применяется внутри такого составного workflow: одна стадия
  может нести несколько наборов ролей (разные инструменты, разные промпты ролей),
  выбираемых аргументом, так что число workflows намного меньше числа режимов запуска.
- **MCP-workflows остаются отдельно.** Два пункта выше верны для встроенных инструментов.
  Роль, которой нужны MCP-инструменты, живёт в своём собственном workflow, потому что
  MCP-сервер может отсутствовать в конкретном проекте, а workflow не должен заявлять
  инструменты, которые он не может получить.

**Fork или workflow.** Любая задача крупнее примерно двух вызовов инструментов бежит либо
как fork-субагент, либо как один из workflows. Что именно — свободный выбор главной
модели. Process skill может рекомендовать вариант для стадии; никакое правило никогда не
фиксирует этот выбор, и class `c1-c5` не имеет к нему отношения. Рассуждение, которое
использует главная модель: fork по построению — самая дорогая модель, но у него самый
дешёвый старт и богатый контекст, что иногда перевешивает цену. Чаще правильный выбор —
более дешёвая модель внутри workflow, потому что текст роли уже готов, а работа может
требовать чтения или записи многих файлов и многих вызовов инструментов.

### 3.3 Process skill

Процесс нескольких ролей на одной большой задаче — это skill. Два существующих process
skill уже показывают рабочую форму, и новый skill её сохраняет:

- **Стадии с gates.** Каждая стадия заканчивается gate с письменным условием
  прохождения (pipeline: R research, D decision, V verification, I implementation, F
  closure check, C closure). Gate — это место, где пользователь может провести review, и
  где смена направления возвращает задачу на более раннюю стадию (изменившееся допущение
  возвращает к decision contract).
- **Носитель не называется.** Process skill (pipeline, review и подобные) фиксирует
  только процесс: стадии, task-файлы, которые каждая стадия читает и пишет (ledger,
  verification plan, implementation plan и остальное из группы ниже), и точки, где
  пользователь проводит review или проясняет. Он никогда не говорит, какой workflow,
  agent или tool решает стадию. Для каждой стадии главная модель сопоставляет
  потребность стадии (research, авторство, запуск oracle, review chain) с workflows,
  agents и tools, которые есть у сессии в этот момент, читая их из usage contract,
  которые плагины внедряют в начале сессии и после compact (3.7). Skill может описывать,
  как выбирать («такие-то виды workflows доступны, действуй через них так-то, готовь эти
  файлы, проходи эти gates»), но не держит списка имён. Причина: недавно включённый
  плагин должен расширять то, что может процесс, без правки process skill; skill,
  называющий носителей, продолжает работать только со встроенными инструментами.
  Research — простой случай: с подключёнными корпоративными инструментами он может
  уходить в метрики, логи, Kubernetes или Slack, и ничего из этого не написано в process
  skill; знание об инструменте живёт только в плагине, который его несёт. Главная сессия
  диктует решения короткими пунктами; она не пишет текста роли.
- **Несколько процессов.** Одна таблица процесса на тип задачи: code change,
  investigation, document, ops change, review чужого MR. Общие правила (task directory,
  ledger, cost rules, harness gate, блоки `Sources` и `Oracles`) живут в одном core-файле,
  который читает каждый процесс первым, как сегодня делает `pipeline/core.md`.
- **Уровни depth `lite`, `std`, `full`.** Depth — это жёсткий список, а не настроение:
  шаг, помеченный `–`, вообще не выполняется, даже если кажется полезным. У каждого
  depth есть ceilings (agents, cycles, turns); достигнутый ceiling завершает стадию, и
  пробел попадает в отчёт. Class и depth приходят от пользователя или из умолчаний ниже;
  главная сессия называет их одной строкой, и на `std` и `full` она начинает работу
  только после intent-вопросов. Аргумент фиксирует depth.
- **Значения по умолчанию.** Когда пользователь не называет class, class — `c3`. Когда
  загружен process skill типа pipeline, depth по умолчанию — `full`, если пользователь
  явно не понижает его.
- **Две независимые оси.** У каждого длинного процесса такого рода есть вес `lite`,
  `std` или `full` в дополнение к class `c1-c5`. Depth говорит, какие стадии и уровни
  артефактов бегут и с какими ceilings; class говорит, на какой модели и effort бежит
  каждая роль (3.4). Ни одно не выводится из другого: `full` на `c2` (каждая стадия,
  дешёвые модели) и `lite` на `c5` (мало стадий, сильные модели) оба допустимы.
- **Сначала intent, с критериями качества.** На `std` и выше первая стадия фиксирует
  intent с пользователем (3.5.2), уточнённый через вопросы прежде, чем что-либо
  строится. На depth `lite` intent gate отсутствует: главная сессия действует сразу на
  основе своего понимания запроса. В том же разговоре (на `std` и выше; показывается ли
  предложение критериев на `lite` — открыто, раздел 9) определяются и согласуются
  критерии качества решения: что из simplicity, extensibility, reliability, performance,
  security и подобного важно для этой задачи, в каком порядке и что не важно. Главная
  сессия предлагает разумный набор по умолчанию, урезанный по depth, а пользователь
  может убрать критерии или добавить свои обратно. Они записываются в task-файлы рядом с
  intent. Каждая последующая стадия их читает: авторы — как ограничения, review chain —
  как источник своих aspect critics по умолчанию (3.6, «Aspect critics»), triage — как
  шкалу severity.
- **Группа task-файлов.** Framing, ledger (unknowns по class: decision-changing,
  verification-changing, implementation-local, nice-to-know), evidence bundles, decision
  contract, verification plan, implementation plan, reviews, report. Файлы несут
  состояние между стадиями, через прерывания, через `/compact` и через сессии. Workflows
  берут их по пути и пишут в них. Каждая стадия возвращает короткий структурированный
  статус (`Status`, `Evidence`, `Assumptions`, `Unresolved`, `Next`); `done` требует
  evidence.
- **Harness gate.** Перед началом работы инструменты, нужные процессу, проходят
  health-check; желаемый инструмент, который недоступен, называется в чате, а не молча
  пропускается.
- **Ограничение импровизации главной модели.** Skill ограничивает процесс, а не
  носителей: какие стадии и файлы есть у depth, что никогда не делается (запрещённый
  список, сформулированный как виды действий, а не как имена), loop guards (одна и та же
  проверка провалилась дважды → стоп и запись failure packet), никакого дополнительного
  цикла без слова пользователя.

### 3.4 Class задаёт модель и effort

Class `c1-c5` задаётся в начале сессии и держится всю сессию; когда пользователь не
называет class, он — `c3`. Правила:

- Каждая роль принадлежит слоту (main-model, opus, sonnet). Строка class в базовой
  таблице, затем submodes (`no-sonnet`, `no-opus`, `no-fable`) дают модель и effort этого
  слота. Ничего другого — нет.
- Каждый workflow, короткий или pool, принимает `class` и `submodes` как аргументы и
  разрешает каждый вызов `agent()` через таблицу. Главная модель передаёт class сессии;
  она никогда не выбирает модель или effort «на глаз», и ни текст роли, ни текст skill не
  называют модель.
- Слот роли следует из характера работы: объём входных данных (большой input сдвигает
  роль на один слот вниз), число механических запросов (много → дёшево), и можно ли
  проверить output (3.5).
- Critic может поднять class задачи, но никогда не понизить (как в `pipeline`). Подъём
  применяется к последующим стадиям.
- Стадия checker для ключевого документа бежит на class на один шаг выше class его
  автора (3.5, правило 3). Это единственный per-stage шаг class; он не меняет class
  сессии.
- Метка каждого агента показывает разрешённую ячейку (`<mod>-<eff>-<job>`), так что
  transcript доказывает, что class был соблюдён.

### 3.5 Правило verification-first

Хорошие тесты всегда сильнее хорошего review. Отсюда:

1. **Output с oracle не получает review.** Код, покрытый тестами, скрипт с исполняемой
   проверкой, конфиг с валидатором: верификатор — это oracle (tests, scenarios, static
   checks, CI job), запускаемый executor'ом. Никакого code review и никакого другого
   review этого output, на любом depth. Тесты и harness-код нельзя тестировать другими
   тестами (тавтология); они пишутся дёшево и не получают review качества, только
   coverage-проверку против списка сценариев (3.5.1, уровень c), а на depth `full` —
   negative control (тест должен падать без изменения).
2. **Output без oracle получает более сильного автора, а не второго читателя.** Для
   объекта, который может проверить только review (decision contract, план, process
   document, код, для которого верификатор невозможен), автор бежит на один шаг выше, чем
   автор тестируемого кода. Шаг читается как один class вверх для этой стадии (`c3` →
   `c4`), а не как повышение уровня модели: повышение уровня (sonnet → opus → fable) было
   бы эффективнее, но для некоторых объектов оно слишком дорого. Пользователь задал этот
   размер для checker'а правила 3; для автора это перенесённая интерпретация, всё ещё
   открытая (раздел 9). Второй читатель того же class — трата. `pipeline` уже применяет это
   к пакетам без верификатора.
3. **Review — не роль по умолчанию, но ключевой документ никогда не остаётся
   непроверенным.** Целевой дизайн не сопоставляет reviewer'а каждому автору.
   Единственное исключение: автор — fork. Fork несёт весь разговор, поэтому его контекст
   смещён; его output идёт к агенту с чистым контекстом. Поэтому critic в pipeline —
   холодный: framing, ledger и contracts там пишут forks. Ключевой документ (план,
   decision contract) никогда не доходит до пользователя без проверки: внимание
   пользователя — самый ценный ресурс, и оно тратится на финальный результат либо на
   стадию, где intent всё ещё неясен и требует, чтобы пользователь задал цель. Поэтому
   каждый ключевой документ получает checker на один class выше автора прежде, чем его
   увидит пользователь; более сильный автор из правила 2 не заменяет эту проверку. Что
   несёт этого checker'а, пользователь не решил (предложение: review chain из 3.6,
   запускаемая с `class` на один шаг выше class автора, так что checker — это стадия, а
   не новая роль); см. раздел 9.
4. **План называет oracle для каждого объекта.** Verification plan сопоставляет каждый
   инвариант или claim с oracle (`existing oracle`, `missing oracle`, `no possible
   oracle`, строки review contract в `session:review`). Строка решает маршрут: запустить,
   построить недостающую проверку и запустить, или правило 2.
5. **То, что остаётся непроверенным, проговаривается.** Области со слабым oracle (ops,
   visual) перечисляются, и пользователь их принимает; они не покрыты мнением.

#### 3.5.1 Verifiability ladder

Объекты различаются тем, насколько сильный oracle у них может быть. От лучшего oracle к
худшему:

| уровень | объект | oracle | проверка |
|---|---|---|---|
| a | код | tests и benchmarks; почти всегда возможны | executor их запускает; никакого review |
| b | изменение инфраструктуры, локальное или удалённое | результирующее состояние: GET-запросы к нему, метрики, логи | control calls, написанные до изменения, запускаемые executor'ом до и после него |
| c | tests и benchmarks | список желаемых test scenarios, написанный заранее как текст в форме, которую выбирает модель (Gherkin, EARS, простые однострочники или любая другая) | только coverage: у каждого сценария есть тест, ни один тест не существует без сценария. Не review качества. Negative control на `full` |
| d | test scenarios | фиксированная спецификация: цель и подзадачи, функциональные и нефункциональные требования, инварианты, ограничения | traceability: у каждого требования, инварианта и ограничения есть хотя бы один сценарий, включая негативные; пробелы проходят через evidence chain (3.6) |
| e | intent: какую проблему хочет решить пользователь, что реализовать, какую систему менять | только пользователь | review-процесс (critic ищет двусмысленность, противоречие, скрытую вторую цель) и разговор с пользователем, проясняющий intent, цель и подзадачи |

Чем ниже уровень в таблице, тем слабее oracle, тем дороже проверка и тем больше нужен
пользователь. Ladder решает маршрут каждого объекта в процессе: process skill никогда не
спрашивает «нужен ли review этому», он спрашивает «какой это уровень».

Coverage на уровне c проверяется чтением, а не скриптом по id: id сценариев в именах
тестов отклоняются, потому что дополнительная связь между двумя текстами расходится, как
только один из них меняется. Агент (`coverage-checker`, слот sonnet) читает список
сценариев и тесты и сообщает о сценариях без теста и тестах без сценария.

#### 3.5.2 Artifact chain

Та же ladder, прочитанная сверху, — это порядок, в котором прорабатывается задача. Он
действует и для не-кодовой работы (документ, ops-изменение, investigation):

intent (цель) → подзадачи (декомпозиция, когда цель сложна) → функциональные требования,
нефункциональные требования, инварианты, ограничения → test scenarios как текст →
исполняемые тесты на языке, либо ручные сценарии control calls → результат (код,
состояние инфраструктуры, документ).

**Каждый уровень — это oracle для уровня ниже него.** Уровень проверяется только против
уровня выше, никогда против разговора или памяти автора. Из 3.5 следует автор каждого
уровня: там, где проверка — только review, автор поднимается.

| уровень | проверяется против | проверка | автор |
|---|---|---|---|
| intent, с критериями качества | пользователь | диалог; critic намекает на неоднозначность; пользователь подтверждает текст. User gate на `std` и `full`; на `lite` главная сессия действует сразу на своём понимании | главная сессия с пользователем; текст пишется на слоте main-model |
| подзадачи | intent | у каждой части цели есть подзадача, ни одна подзадача не лежит вне цели; evidence chain; user gate на `std` и `full` | uplift: слот main-model |
| требования, инварианты, ограничения | intent и подзадачи | traceability к подзадачам, нет противоречий, у каждого нефункционального требования есть измеримая форма; evidence chain | uplift: на один шаг выше автора кода (размер открыт, раздел 9) |
| test scenarios как текст, в форме, которую выбирает модель | спецификация | traceability: у каждого требования и инварианта есть сценарии, включая негативные; проверка чтением, critic только для пропущенных случаев | uplift: на один шаг выше автора кода (размер открыт, раздел 9; coverage проверяема, смысл сценария — нет) |
| исполняемые тесты, control calls | сценарии | coverage чтением двух списков; negative control на `full`; никакого review качества | без uplift: дешёвый автор |
| результат: код, состояние инфраструктуры | тесты, control calls | запуск executor'ом | без uplift: самый дешёвый автор, который допускает class |
| результат без возможного oracle (документ) | сценарии, как чек-лист, на который может ответить читатель | evidence chain с aspect critics | uplift: на один шаг выше автора кода (размер открыт, раздел 9) |

Два следствия:

- Ошибка выше по цепочке — самая дорогая: каждый уровень ниже верно проверяется против
  неё, и неверный intent даёт зелёные тесты для неправильной вещи. Поэтому деньги и
  внимание пользователя идут на верх цепочки, а низ бежит дёшево.
- Цепочка отображается на существующие файлы pipeline: `Framing` — это intent, инварианты
  `Decision contract` — часть спецификации, `Verification plan` (карта invariant → oracle,
  сценарии, негативные сценарии) содержит сценарии, harness содержит тесты. Чего не
  хватает pipeline — перечислено в разделе 7.

На depth `lite` уровни схлопываются (intent, подзадачи и требования в одном коротком
тексте, сценарии в короткой форме, которую выбирает модель, например однострочники), но
их порядок и правило «проверяется против уровня выше» сохраняются.

### 3.6 Review как цепочка доказательств

Там, где review всё же бежит (правило 3 из 3.5, или review чужой работы), reviewer не
выдаёт верные суждения. Он может только указать места, где может скрываться ошибка.
Каждое указание затем доказывается или опровергается фактами. Четыре роли, один pool
workflow:

| стадия | роль | что делает | слот |
|---|---|---|---|
| 1 | `critic` | читает объект в чистом контексте; пишет hints: место, подозреваемая ошибка, severity, какое доказательство это решит. Hints, не вердикты. Только Read и Write, бюджет вызовов инструментов. | main-model |
| 2 | `evidence-researchers` | параллельно, по одному на hint или группу hints; собирают факты через research, прогоны тестов, прогон на базовой версии, документацию. Возвращают `confirmed`, `refuted` или `undetermined` с указателями. Много дешёвых запросов. | sonnet |
| 3 | `evidence-triage` | судья: читает критику и evidence, принимает или отклоняет каждый hint, пишет принятый список с требуемым изменением. Сам никаких запросов не выполняет. | слот main-model (или слот opus ниже `c4`, открытый вопрос) |
| 4 | `fixer` | меняет объект только по принятому списку; затем запускается oracle, если он есть. | opus |

Правила цепочки:

- Hint без evidence ничего не меняет. Hint `undetermined` уходит к пользователю через
  `session:ask`; он никогда не доходит до fixer.
- Два вида отказа держатся раздельно (из `session:review`): находка об объекте и отказ
  harness на нашей стороне (инструмент, доступ, sandbox). До triage доходит только первый.
- Контрольный прогон защищает от ложных находок: отказ, который проявляется и на
  базовой версии, — не находка.
- Один раунд: generate → critique → evidence → triage → fix, без второй critique без
  слова пользователя (heavy document cycle из `pipeline`).
- Форма следует за depth. Короткая форма для depth `lite` и `std`: стадии 2 и 3
  сливаются в один агент `evidence` на более низком слоте, который и собирает, и решает
  (evidence-audit из pipeline). Длинная форма для `full` и для любого намёка на высокий
  severity.

**Aspect critics.** Стадия 1 может разделиться на несколько параллельных critics. Каждый
читает один и тот же объект через один аспект качества и даёт hints только по этому
аспекту: simplicity, reliability, security, extensibility, performance, scalability и
подобные (testability, operability, data integrity, cost). Узкий вопрос находит больше,
чем общее «ищи проблемы», и аспекты не конкурируют за внимание или бюджет инструментов
одного critic.

- **Набор aspect на задачу.** Не каждый aspect подходит каждому объекту: у process
  document нет aspect performance, у внутреннего скрипта нет aspect scalability. Набор
  выбирается под задачу. Главная сессия предлагает разумный набор по умолчанию, урезанный
  до количества, которое допускает depth (эти количества — предложение, не решённое:
  `lite` — один слитый critic без разделения по aspect, `std` — 2-3 aspect, `full` — 3-5
  aspect; пользователь решил только то, что depth ограничивает список), и это
  предложение всегда идёт к пользователю на утверждение: пользователь может убрать aspect
  или добавить свои критерии обратно. Утверждённый список записывается в task-файлы
  рядом с intent (3.3). Ни один aspect critic не бежит без этого утверждения, даже
  `security`. На `lite` это встречается с отсутствующим intent gate из 3.3; как они
  встречаются там — открыто (раздел 9).
- **Статические aspect-промпты.** Workflow хранит один общий текст роли critic (чистый
  контекст, hints, а не вердикты, формат hint, бюджет) плюс один короткий статический
  абзац на аспект: что аспект означает, типичные формы ошибок, что вне scope. Аргумент
  `aspects` — список имён из этого фиксированного каталога; он выбирает абзацы и не несёт
  текста промпта. Неизвестное имя останавливает workflow. Новый аспект — новый абзац в
  скрипте, проверяемый один раз.
- **Формат hint.** Каждый hint несёт `aspect`, `place` (файл и диапазон строк, или раздел
  документа), подозреваемую ошибку, severity и доказательство, которое бы это решило. У
  каждого critic есть предел hints (предложение: 5), так что N critics дают не более
  5 × N hints.
- **Слияние и dedupe, в скрипте.** Без дополнительного агента. Скрипт объединяет списки
  hints и группирует их по `place`; hints на одном или пересекающемся месте образуют одну
  группу, сохраняющую все свои aspect-теги. Одна группа идёт к одному
  evidence-researcher, так что два critic, указавших на одни и те же строки, стоят один
  прогон evidence, а не два. Группа получает наивысший severity из своих hints. Hints
  с одинаковым смыслом на разных местах остаются раздельными; triage видит весь список с
  тегами и может принять их как одно изменение. Место, названное несколькими аспектами, —
  полезный сигнал для triage, а не шум.
- **Слот по таблице class.** Aspect critics разрешаются через таблицу, как и любая роль;
  ни у одного аспекта нет своей модели. Предложение: единственный слитый critic остаётся
  на слоте main-model; когда стадия разделяется на 2 или более aspect critics, каждый
  бежит на слоте opus, потому что узкий вопрос требует от модели меньше, а иначе дорогое
  чтение умножалось бы на N. Большой input сдвигает их ещё на один слот вниз по обычному
  правилу. `evidence-triage` остаётся единственным дорогим суждением по всем аспектам.
- **Стоимость.** Стадия critic стоит N × (одно чтение объекта плюс короткий список hints);
  разделение умножает чтение, поэтому слот понижается по мере роста N. Стадия evidence
  растёт с числом групп hints, а не с числом critics, и предел hints её ограничивает.
  Ceilings по depth считают aspect critics как agents. Для небольшого объекта на depth
  `lite` разделение стоит дороже, чем находит; правило там — один слитый critic.

Выгода: выбор модели по стадии (одно дорогое чтение или несколько более дешёвых узких
чтений, много дешёвых поисков, одно дорогое суждение), и изменение объекта опирается на
факты, а не на догадку модели.

### 3.7 Модель подключения: добавление на уровне пользователя, изъятие по проекту

Как плагины, tools, agents, workflows и skills доходят до проекта. Сформулировано
пользователем; это определяет разбиение всего дизайна на плагины.

- **Уровни.** Уровень пользователя, уровень проекта, а между ними — плагины, группирующие
  вещи. Базовый плагин несёт базовый skill и всё для встроенных инструментов.
- **Плагин — единица поставки.** Плагин может нести MCP-серверы (новые инструменты),
  lean-агентов, построенных под эти инструменты, workflows, которые их предполагают,
  hooks, внедряющие usage contract этих workflows как системные напоминания в начале
  сессии и после compact, и process- или context-skills.
- **Уровень пользователя только добавляет.** Каждый нужный плагин включается на уровне
  пользователя, так что по умолчанию у любого проекта самый богатый набор.
- **Уровень проекта только забирает.** Два средства: `permissions.deny` для тяжёлых
  встроенных инструментов, не нужных проекту (Artifact, design tools), и отключение
  целого плагина, чьи инструменты проекту не нужны.
- **Плагин ничего не может отключить.** Он только добавляет.
- **Назначение.** Управление контекстным окном: разрешать всё на уровне пользователя,
  запрещать отдельные элементы по проекту, и так контролировать, что подключено и что
  сидит в контексте.

Следствия для дизайна:

- Общий плагин хранит носителей для встроенных инструментов; каждый MCP-сервер или
  группа инструментов получает собственный плагин со своими agents, workflows, hooks и
  skills (3.1, 3.2 «MCP-workflows остаются отдельно», 8.12).
- Process skills находят носителей через внедрённые contract'ы и не называют ни одного
  (3.3), так что включение или отключение плагина меняет, что может использовать
  процесс, без правки где-либо.
- Предложение главной сессии, не слова пользователя: каждый плагин самодостаточен. Его
  agents, workflows, hooks и skills работают вместе или исчезают вместе, и ничто вне
  плагина не зависит от инструмента, который проект может запретить, или от плагина,
  который проект может отключить. Открыто в разделе 9.

## 4. Цели

1. Один носитель на аспект: инструменты в файлах агентов, роли в workflows,
   фиксированные потоки в pool workflows, процесс задачи в skill.
2. Убрать написание промптов из главной модели: запуски несут аргументы, а не текст
   роли.
3. Модель и effort каждого агента приходят из class сессии и слота роли, никогда — из
   выбора, сделанного при запуске.
4. Верификация через oracle в первую очередь: review бежит только там, где oracle
   невозможен и контекст автора смещён, а ключевой документ никогда не остаётся
   непроверенным, кем бы он ни был написан.
5. Review меняет объект только через evidence: hint → факты → суждение → fix.
6. Сделать работу над задачей повторяемой: один и тот же тип задачи и depth дают одни и
   те же стадии, одни и те же роли и одни и те же артефакты.
7. Сделать работу прерываемой: задача может остановиться ради пользователя и
   возобновиться из файлов.
8. Соответствие трат задаче по двум независимым осям: depth (`lite`, `std`, `full`)
   решает, что бежит, class (`c1-c5`) решает, на каких моделях.
9. Держать project-специфичные и MCP-инструменты вне общего плагина: каждая группа
   инструментов живёт в своём плагине со своими agents, workflows, hooks и skills.
10. Прорабатывать одну artifact chain и для кодовых, и для не-кодовых задач: intent →
    подзадачи → требования и инварианты → test scenarios → исполняемые тесты →
    результат. Каждый уровень проверяется только против уровня выше, той проверкой,
    которую позволяет его уровень ladder.
11. Согласовывать intent и критерии качества с пользователем прежде, чем что-либо
    строится, на `std` и выше, и позволять критериям направлять последующие проверки;
    `lite` действует сразу.
12. Контролировать контекст по проекту вычитанием: всё добавляется на уровне
    пользователя, проект запрещает встроенные инструменты и отключает плагины, плагин
    только добавляет (3.7).
13. Держать process skills открытыми для расширения: они не называют ни workflow, ни
    agent, ни tool, так что недавно включённый плагин расширяет то, что может процесс,
    без правки skill (3.3).

## 5. Проблемы, которые это решает

- **Дрейф ролей.** Главная модель каждый раз пишет новый промпт critic или researcher;
  качество и формат возврата различаются между запусками.
- **Стоимость output-токенов запусков.** Промпт на 300-1000 токенов на агента пишет
  самая дорогая модель. Со статическими ролями запуск — это имя плюс аргументы.
- **Взрыв числа файлов агентов.** Когда роль и набор инструментов живут в одном файле,
  каждая новая роль требует нового агента. Разделённо, N наборов инструментов и M ролей
  дают N + M файлов, а не N × M.
- **Модель, выбираемая на глаз.** Главная модель выбирает модель и effort на каждый
  запуск; одна и та же роль бежит на разных моделях в одной сессии, и class, заданный
  пользователем, не соблюдается.
- **Review там, где тесты сильнее.** Code review протестированного кода стоит полного
  чтения на дорогой модели и доказывает меньше, чем прогон теста.
- **Мнения review, принимаемые за факты.** Замечание reviewer'а идёт напрямую к fixer;
  неверное замечание портит корректный объект и стоит цикла исправления.
- **Слабые авторы для непроверяемых объектов.** План или contract, написанный на дешёвом
  слоте и затем «спасённый» читателем того же class, стоит два прогона и всё равно не
  доказан. Checker на один class выше автора (3.5, правило 3) — решённое исключение.
- **Импровизированный процесс.** Главная модель решает на ходу, стоит ли сначала
  исследовать, сколько циклов запускать. Она перетрачивает на мелких задачах и
  недотрачивает на рискованных.
- **Одноразовые workflows нельзя направлять.** Полный workflow разработки бежит от плана
  до закрытия без точки для смены направления или human review.
- **Потерянное состояние.** Без фиксированной группы файлов состояние задачи живёт в
  разговоре; compact, новая сессия или рестарт по лимиту теряют его.
- **Project-инструменты в общем плагине.** Агенты с project MCP-инструментами не место в
  плагине, который загружает каждый проект.
- **Процесс, привязанный к фиксированному набору инструментов.** Process skill,
  называющий свои workflows и agents, продолжает работать только со встроенными
  инструментами; подключение плагина с новыми инструментами (метрики, логи, Kubernetes,
  Slack) не добавляет процессу ничего, пока skill не отредактирован.
- **Нет способа урезать контекст по проекту.** Тяжёлые инструменты и неиспользуемые
  плагины сидят в контексте каждого проекта, если проект не может их запретить или
  отключить.

## 6. Что станет лучше после реализации

Целевые показатели; сначала нужно измерить baseline (транскрипты под
`~/.claude/projects`).

- Output-токены главной сессии на запуск агента: с 300-1000 (текст промпта) до менее 100
  (имя и аргументы).
- Доля запусков по имени против ad hoc скриптов: свыше 80 %.
- Соответствие class: 100 % меток агентов совпадают с ячейкой class сессии и слотом роли.
- Reviews output с проходящим oracle: ноль.
- Исправления без принятого evidence: ноль; каждое изменение, сделанное fixer, указывает
  на строку triage, а та строка — на указатель evidence.
- Точность hints: доля hints critic, подтверждённых evidence, измеряется на процесс;
  низкая доля — сигнал изменить промпт critic, а не добавить второго critic.
- Переделка, вызванная неверным замечанием review: снижается, поскольку опровергнутый
  hint никогда не доходит до fixer.
- Стоимость review chain против одной дорогой пары reviewer-плюс-fixer: равна или ниже,
  поскольку многочисленные запросы бегут на слоте sonnet.
- Стоимость задачи по depth: у `lite`, `std`, `full` заявленные ceilings; количество
  строк ledger проверяется против них.
- Переделка после поздней находки: gate после стадии decision останавливает неверное
  направление до implementation.
- Возобновление: задача продолжается после `/compact`, новой сессии или рестарта по
  лимиту из task-файлов без повторного research.
- Сопровождение: роль меняется в одном файле workflow; набор инструментов — в одном файле
  агента; процесс — в одном skill; карта моделей — в одной таблице.

## 7. Разрыв с текущим плагином `session`

Проверено: `plugins/session/agents/`, `workflows/`, `workflows/dev.js`,
`skills/pipeline/SKILL.md`, `skills/review/SKILL.md`, базовый skill. Внутренности
workflows, кроме `dev.js`, взяты из их контрактов, а не из скриптов.

**Уже есть**

- Lean-агенты с сокращёнными списками инструментов: `stage-author` (Bash, Read, Edit,
  Write), `stage-reviewer` и `stage-critic` (Read, Write), `stage-executor` (Bash, Read),
  `stage-researcher`, `translator`, `waiter`, `web-researcher`.
- Pool workflows с фиксированным потоком: `dev`, `build`, `review-fix`, `research`.
  Промпты ролей — статический текст внутри скриптов; `class` и `submodes` — аргументы, и
  таблица class разрешает модель и effort по слоту.
- Один короткий workflow, близкий к типу single-agent: `translate-ru`.
- Контракты workflows доходят до главной сессии как контекст SessionStart.
- Два process skill целевой формы: `session:pipeline` (gates R, D, V, I, F, C; пути fast,
  standard, full как жёсткие списки с ceilings; task directory, ledger, evidence bundles)
  и `session:review` (пути `lite`, `std`, `full`, `re`; review contract со строками
  oracle; findings только из прогонов; control run на базовой ветке).
- Verification-first прописан в обоих: «В этом режиме нет code review», пакет без
  верификатора получает более сильного автора и никакого читателя, тесты никогда не
  проходят review.
- Частичная evidence chain: холодный critic pipeline → triage главной сессии →
  evidence-audit fork → низкий fixer fork, один раунд; `review-fix` называет «critique,
  evidence check, fixes, tests» в своём контракте.

**Отсутствует или смешано**

- Базовый skill противоречит verification-first: «каждая стадия авторства сопряжена с
  независимым review», code review каждого diff свыше 100 строк, критика плана и closure
  review как минимум для каждой кодовой задачи. `dev` и `build` следуют базовому skill, а
  не pipeline.
- Нет роли `evidence-triage`. В `pipeline` главная сессия сама проводит triage, по
  собственному суждению и в собственном контексте; evidence — один fork, а не группа
  дешёвых researchers. Ни один pool workflow не запускает четырёхстадийную цепочку для
  произвольного объекта.
- `stage-reviewer` существует как роль с вердиктами; дизайн хочет critic, дающего hints и
  оставляющего вердикты triage.
- Правило более сильного автора зашито как имена моделей ("opus-low", "terra-high") в
  `pipeline`, а не как «на один шаг выше» из таблицы class. `session:review` фиксирует
  свою главную сессию на opus-low в тексте. Оба нарушают «никаких имён моделей в skills».
- Стадии fork в `pipeline` и `review` наследуют модель главной сессии, так что class ими
  не управляет; только холодные стадии следуют таблице.
- Файлы агентов всё ещё несут роли в именах и телах ("author", "reviewer", "critic");
  семейство наборов инструментов не именовано по инструментам и неполно (нет агента
  только с Read, нет вариантов MCP).
- Нет коротких single-agent role workflows для общих ролей (критика одного документа,
  один research-вопрос, запуск одной тестовой команды, triage). Базовый skill говорит
  главной сессии писать ad hoc скрипт с промптом на 300-1000 токенов вместо этого. Это
  самый крупный разрыв.
- `pipeline` и `review` запускают стадии через forks с промптами, диктуемыми главной
  сессией, а не через именованные workflows; роли всё ещё пишутся на лету.
- Базовый skill и оба process skill называют носителей в своём тексте (типы agents,
  имена workflows, стадии forks), так что новый плагин не может расширить их без правки.
- `dev` — одноразовый прогон от плана до закрытия без остановки для пользователя.
- Таблицы процесса существуют только для своей кодовой задачи и review MR; investigation,
  document и ops названы в описании pipeline, но не имеют таблицы.
- Имена depth различаются (`fast/standard/full` против `lite/std/full`), и depth
  выводится из class в обоих skills.
- Два места и формы task-файлов: `~/.claude/projects/.../pipeline/<task>` для skills,
  `<cwd>/reviews` для workflows.
- Нет паттерна project-group плагина (агенты b2connect живут в `.claude` проекта, что
  соответствует идее, но не имеет именования наборов инструментов).
- Общий блок (таблица class, `opts`, `cycle`) копируется в каждый скрипт; больше коротких
  workflows умножают копии.
- Workflow не проверяет, что выходной файл стадии существует (видно сегодня в
  `translate-ru`: агент вернул путь и ничего не записал). `done` без evidence проходит.
- Artifact chain присутствует лишь частично. У `pipeline` есть `Framing`, `Decision
  contract` с инвариантами и `Verification plan` с картой invariant → oracle, но: нет
  gate, где пользователь подтверждает intent (главная сессия предлагает и начинает и на
  `std`, и на `full`); нет собственного уровня спецификации (функциональные и
  нефункциональные требования, ограничения); нет coverage-проверки тестов против
  сценариев (быстрый путь пишет «один новый тест на изменённое поведение» без списка
  сценариев). `dev` начинается в середине цепочки: он берёт «задачу с acceptance
  criteria», и ничто не проверяет criteria против intent.
- Нет ladder: skills знают два случая (есть верификатор, нет верификатора). У изменений
  инфраструктуры нет именованной проверки control calls против результирующего состояния;
  `pipeline` только называет ops слабым oracle.
- Критерии качества решения не запрашиваются, не записываются и не используются; critic
  читает без шкалы, согласованной с пользователем.

## 8. Подзадачи реализации

Порядок следует зависимостям; пункты на одном уровне могут бежать параллельно.

1. **Инвентаризация и именование наборов инструментов.** Перечислить комбинации
   инструментов в реальном использовании (файлы агентов и transcripts), выбрать
   семейство и имена по набору инструментов. Весь набор agents, workflows, hooks и
   process skills пересобирается с нуля под новыми именами; старые зачищаются, и
   сохранённые скрипты, вызывающие старые имена, не поддерживаются в рабочем состоянии.
   Результат: таблица агентов. Зависит от: ничего.
2. **Каталог ролей со слотами.** Роли: plan author, code author, test author, fixer,
   critic, evidence-researcher, evidence (слитая короткая форма), evidence-triage,
   researcher, executor, translator, web researcher, и роли цепочки из 3.5.2: spec
   author, scenario author, coverage-checker. Для каждой: статический промпт, аргументы,
   формат возврата, агент с набором инструментов, слот и правило, сдвигающее слот
   (объём input, no-oracle uplift). Нигде никаких имён моделей. Checker ключевого
   документа (3.5, правило 3) тоже фиксируется здесь: либо review chain бежит на один
   class выше, как предложено, либо своя отдельная роль, когда носитель будет решён
   (раздел 9). Зависит от: 1.
3. **Спецификация verification-first.** Классы oracle (`existing`, `missing`, `no
   possible`), маршрут по классу, размер uplift автора для объектов без oracle,
   исключение fork-автора, как принимаются непроверенные области. Verifiability ladder
   (уровни a-e) с проверкой на уровень, control calls для изменений инфраструктуры, и
   artifact chain с автором на уровень. Текстовая форма сценария свободна: модель
   выбирает её под задачу, а документ только перечисляет известные формы (Gherkin, EARS,
   простые однострочники) как подсказки. Никаких id сценариев и никакого id в имени
   теста; coverage проверяется чтением двух списков. Одна страница, на которую ссылаются
   core-файл и workflows.
   Зависит от: ничего.
4. **Стратегия общего блока.** Шаг сборки, штампующий таблицу class и helpers в каждый
   скрипт, плюс тест, что все копии совпадают; блок также несёт проверку
   "output exists" для каждой стадии, называющей выходной файл. Зависит от: ничего;
   нужен перед 5.
5. **Role workflow.** Один workflow для одиночных агентов с аргументом `role`; его usage
   contract перечисляет роли, которые он несёт, так что один скрипт и одна строка
   SessionStart покрывают весь каталог, а сопровождение остаётся в одном месте. Тот же
   подход применяется внутри составных workflows: стадия может нести несколько наборов
   ролей (разные инструменты, разные промпты ролей), так что число workflows намного
   меньше числа режимов запуска. Результат включает hooks: один новый contract-hook
   SessionStart для role workflow, и старые per-workflow hooks удалены вместе со старым
   набором (8.1, 8.11). Это верно для встроенных инструментов. Роли, которым нужны
   MCP-инструменты, остаются в отдельных workflows, потому что MCP-сервер может
   отсутствовать в конкретном проекте, а workflow не должен заявлять инструменты,
   которые он не может получить. `class` и `submodes` как аргументы. Протестировать
   каждую роль в tmux-сессии. Зависит от: 2, 4.
6. **Review-chain pool workflow.** `critic → evidence-researchers → evidence-triage →
   fixer`, длинная и короткая форма по аргументу `depth`, один раунд, отказы harness
   держатся раздельно, control run, принятый список как файл. Aspect critics:
   фиксированный каталог статических aspect-абзацев в скрипте, аргумент `aspects`
   (список имён каталога; по умолчанию: набор, утверждённый пользователем и читаемый из
   task-файлов, количество по depth, сами количества — предложение, раздел 9),
   параллельные critics с пределом hints, группировка hints по месту на стороне скрипта
   перед стадией evidence, правило слота для разделённой стадии critic, aspect critics
   учитываются в ceilings по depth. Тест: два critic, указавших на одни и те же строки,
   дают один прогон evidence. Это новый workflow под новым именем; старый `review-fix`
   удаляется вместе с остальным (8.1, 8.11). Зависит от: 2, 3, 4.
7. **Новые pool workflows под verification-first.** Преемники `dev` и `build`, написанные
   с нуля под новыми именами: никакого reviewer для тестируемого кода (author → tests →
   fixer), пакеты без oracle — к более сильному автору, документы, написанные fork —
   в review chain, checker на один class выше для каждого ключевого документа. Каждый
   gate старого `dev` становится workflow, который может бежать отдельно. Зависит от: 3,
   6.
8. **Группа task-файлов.** Одна раскладка для каждого процесса и depth: файлы живут под
   `~/.claude/projects/.../`, как skills хранят их сегодня; имена файлов, какая стадия
   какой файл пишет, маркеры статуса, правило возобновления. Один артефакт на уровень
   цепочки: intent с критериями качества (подтверждённый пользователем на `std` и `full`,
   с датой; на `lite` написанный главной сессией самостоятельно), подзадачи,
   спецификация, сценарии, отчёт о покрытии последней проверки (не поддерживаемая карта
   scenario → test). Схлопнутая форма для `lite`. Согласовать умолчания `out` workflow с
   этим. Зависит от: ничего; нужен перед 9.
9. **Новый process skill на workflows.** Новый skill под новым именем, перенимающий
   форму `pipeline` и `review`: core-файл, gates, таблица depth с жёсткими списками и
   ceilings, блоки `Sources` и `Oracles`, harness gate, loop guard, структурированный
   статус. Стадия не называет ни workflow, ни agent, ни tool: она формулирует
   потребность, task-файлы, которые читает и пишет, и свой gate, а главная модель
   сопоставляет её с носителями, которые есть у сессии, читая их из внедрённых
   contract'ов (3.3, 3.7). Skill может рекомендовать fork или workflow как вид; этот
   выбор делает главная модель, и никакое правило его не фиксирует (3.2). Depth и class
   как два независимых аргумента. Стадии следуют artifact chain; первая стадия —
   разговор об intent с пользователем (intent, подзадачи, критерии качества) и
   заканчивается user gate на `std` и `full`; на `lite` она начинается сразу без gate.
   Загруженный process skill типа pipeline задаёт depth по умолчанию `full`, а class по
   умолчанию `c3`. Первый процесс: code change. Зависит от: 5, 6, 7, 8.
10. **Больше процессов.** Review MR (перенос `session:review`), investigation, document,
    ops change: каждый — таблица процесса над тем же core. Зависит от: 9.
11. **Переписывание базового skill и зачистка старого набора.** Убрать «каждая стадия
    авторства сопряжена с review», обязательный code review и closure review; заявить
    verification-first, review chain, «class задаёт модель и effort», «запуск по имени;
    ad hoc скрипт — исключение». Никаких имён моделей в тексте skill. Удалить старые
    agents, workflows, hooks и process skills (`pipeline`, `review`, `dev`, `build`,
    `review-fix`, агенты `stage-*` и их SessionStart contract-hooks); предложение
    относительно момента удаления, не решённое пользователем: как только их преемники
    пройдут свои тесты. Зависит от: 3, 9.
12. **Паттерн плагина для инструмента.** Шаблон и реальные случаи (подключённые сегодня
    MCP-серверы, b2connect): один плагин на MCP-сервер или группу инструментов, несущий
    сервер, файлы агентов с его инструментами, отдельные MCP-workflows, которые их
    используют (встроенный role workflow из 8.5 никогда не несёт MCP-ролей),
    contract-hooks и любые skills. Включается на уровне пользователя, отключается по
    проекту; тяжёлые встроенные инструменты запрещаются по проекту через
    `permissions.deny` (3.7). Process skill находит носителей через внедрённые
    contract'ы, никогда по имени. Зависит от: 1, 5.
13. **Behavior tests.** Сценарии `test-session`: запуск по имени без промпта роли;
    метки агентов совпадают с ячейкой class при c2, c3, c5 и одном submode; никакого
    review, когда oracle существует; посаженный ложный hint опровергается и никогда не
    доходит до fixer; посаженный реальный дефект подтверждается и исправляется; `lite`
    пропускает то, что должен пропустить; задача возобновляется из файлов после
    `/clear`; на `std` и `full` ни одна стадия не начинается до подтверждения intent
    пользователем, на `lite` работа начинается сразу; сценарий без теста и тест без
    сценария оба сообщаются проверкой coverage, без id в именах тестов; aspect, который

## 9. Открытые вопросы для пользователя

Пункты обратной связи 1-17 по вопросам 1-15 ревизии 3, отвеченные пользователем; решённые
несут разделы тела документа:

1. `reviewer` убирается как роль; `critic` плюс evidence chain остаются (3.5, 3.6).
2. Ключевой документ никогда не доходит до пользователя непроверенным; внимание
   пользователя идёт на финальный результат либо на стадию, где intent всё ещё неясен
   (3.5, правило 3).
3. Checker ключевого документа бежит на один class выше автора, а не на один уровень
   модели выше: шаг уровня модели был бы эффективнее, но для некоторых объектов слишком
   дорог (3.5, правило 3). Тот же размер переносится на uplift автора из правила 2 как
   интерпретация, а что несёт checker — открыто; см. «Ещё открыто».
4. Не решено: вопрос 3 ревизии 3 (`evidence-triage`: всегда слот main-model, или слот
   opus ниже `c4`) получил «Looks good» на выбор из двух без предложения, так что ни один
   вариант не назван; см. «Ещё открыто» 3.
5. Цепочка длинная для `full` и для любого hint с высоким severity, короткая в остальных
   случаях (3.6).
6. Hints `undetermined` уходят к пользователю через `session:ask` (3.6).
7. Новый process skill — следующая версия `pipeline` и `review` по функции, одно ядро; по
   пункту 10 он строится с нуля под новым именем, так что «те же имена» из текста
   ревизии 3 не действуют (8.9, 8.11).
8. Class по умолчанию `c3`, когда пользователь не называет ни одного; depth по умолчанию
   `full`, когда загружен process skill типа pipeline, если пользователь его не понижает
   (3.3, 3.4).
9. Fork или workflow — свободный выбор главной модели, опционально рекомендуемый process
   skill, никогда не зафиксированный правилом и никогда не привязанный к class (3.2).
10. Agents, workflows, hooks и process skills пересобираются с нуля под новыми именами;
    старые зачищаются, и сохранённые скрипты не поддерживаются в рабочем состоянии (8.1).
11. Один role workflow с аргументом `role` и ролями, перечисленными в его контракте;
    составные workflows могут нести несколько наборов ролей на стадию; workflows,
    которым нужны MCP-инструменты, остаются отдельно от workflows на встроенных
    инструментах (8.5).
12. Группа task-файлов живёт под `~/.claude/projects/.../` (8.8).
13. Список aspect — разумный набор по умолчанию, урезанный по depth, и всегда идёт к
    пользователю, который может его урезать или добавить критерии; ни один aspect не
    бежит без этого утверждения, и более раннее предложение «security бежит всегда»
    снято (3.3, 3.6).
14. Id сценариев в именах тестов отклоняются: дополнительная связь между двумя текстами
    расходится. Coverage проверяется чтением (3.5.1, 3.5.2, 8.3).
15. Форма сценария свободна; модель выбирает её, а документ только перечисляет известные
    формы как подсказки (3.5.1, 8.3).
16. На `lite` главная сессия действует сразу без intent gate; на `std` и выше intent
    уточняется с пользователем через вопросы (3.3, 3.5.2).
17. Для изменения инфраструктуры control calls (GET-запросы, метрики, логи) пишутся как
    файл команд с ожидаемыми результатами до изменения и запускаются до и после него;
    это принятая форма «тестов» для ops-работы (3.5.1, уровень b).

Решено двумя продиктованными заметками после прочтения (addendum):

18. Модель подключения: каждый нужный плагин включается на уровне пользователя и несёт
    свои MCP-серверы, lean-агентов, workflows, contract-hooks и skills; проект только
    забирает, через `permissions.deny` для тяжёлых встроенных инструментов и через
    отключение плагина; плагин ничего не может отключить (3.7).
19. Process skills (pipeline, review) не называют ни workflow, ни agent, ни tool. Они
    фиксируют стадии, task-файлы и точки review пользователя; главная модель
    сопоставляет каждую стадию с тем, что есть у сессии, так что новый плагин расширяет
    процесс без правки skill (3.3).
